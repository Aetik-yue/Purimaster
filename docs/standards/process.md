# 开发过程规范

- **版本**: v0.1 ｜ **日期**: 2026-11-03 ｜ 适用范围：Purimaster 全部开发活动

---

## 1. 分支模型

```
main          ← 永远可构建、可测试，受保护
└── feat/<slug>     功能分支（如 feat/junk-scanner）
├── fix/<slug>      缺陷修复
└── docs/<slug>     文档专项
```

- 不设 develop 分支，个人/小团队规模用简化模型
- 功能分支生命周期 ≤ 1 周，超期拆分
- 合入 main 一律走 PR（哪怕自己合自己），PR 描述写清做了什么、怎么验证的

## 2. 提交规范（Conventional Commits）

格式：`<type>(<scope>): <中文描述>`

| type | 用途 |
|------|------|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档 |
| `refactor` | 重构（不改行为） |
| `test` | 仅测试 |
| `chore` | 构建、依赖、工程配置 |

示例：

```text
feat(core): 实现并行目录遍历
fix(rules): 修复 Temp 规则未排除当前会话锁定的文件
docs: 建立文档编写规范
```

- 一个提交做一件事；scope 用 crate/模块名（core / rules / platform / app / web）
- **每次提交必须通过质量门禁**（见 §5），不允许"先提交再修"

## 3. 开发工作流

每个功能按此循环：

1. **对齐** — 在需求/架构文档中能找到该功能的定位；找不到就先补文档
2. **计划** — 列实现要点与验收标准（可写在 PR 描述或 devlog 中）
3. **测试先行** — `crates/` 内逻辑先写失败的单测再实现（TDD）
4. **实现** — 小步提交
5. **自审** — 过一遍 diff，对照验收标准
6. **PR 合入** — CI 绿 + 文档同步更新

### 危险操作红线（删除相关代码）

- 任何删除实现必须支持 **dry-run** 模式
- 永久删除路径必须有二次确认逻辑，且单测覆盖"确认前不删"
- 系统关键路径（Windows、Program Files 等）排除规则**硬编码在 `crates/platform`**，不依赖用户配置
- 涉及删除逻辑的 PR，描述中必须说明测试了哪些"不会误删"场景

## 4. 测试策略

| 层 | 要求 |
|----|------|
| `crates/*` 单测 | 核心逻辑（遍历、聚合、去重、规则匹配）必须单测覆盖；用 `tempfile` 构造临时目录夹具，禁止依赖真实磁盘内容 |
| 删除安全 | dry-run / 二次确认 / 关键路径排除，三者的负向用例必测 |
| 集成测试 | `tests/` 下针对 Tauri command 层，MVP 后补 |
| 手工验收 | 每个版本发布前跑一遍需求文档的验收条款，记录到 devlog |

## 5. 质量门禁（每次提交前）

```bash
cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
pnpm lint && pnpm build   # 前端侧，进入 UI 开发后启用
```

clippy 不允许用 `#[allow]` 压警告，除非代码注释说明理由。

## 6. 版本策略

- 语义化版本（SemVer）；v1.0 前处于 0.x，允许破坏性变更（需在 devlog 声明）
- 发布打 git tag：`v0.1.0`，附发布说明

## 7. 开发日志制度

- **每个开发工作日**至少一篇，写进 `devlog/`，格式见[文档规范](documentation.md)
- 内容必须如实记录：做完了什么、没做完什么、卡在哪，不写"顺利""正常"这类空话
- 所有偏离规范/文档的决定，当天的 devlog 必须记录原因
