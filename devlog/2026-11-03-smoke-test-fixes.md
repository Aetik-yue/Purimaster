## 遇到的问题与解决

1. **冒烟测试反馈：进度条不动、取消"没用"**
   - 排查路径：静态配置逐项核实（事件名合法性 ✓、capabilities 编译产物含 event 权限 ✓、@tauri-apps/api 版本匹配 ✓）→ 真盘无 UI 验证引擎（进度/取消正常）→ 病灶锁定 Rust→前端事件链路
   - 两个症状实为同一根因：进度/完成/取消结果全靠事件推送，链路断则全部失效（取消可能已生效，只是"已取消"事件丢失，UI 永远停在"正在扫描"）
   - 处置：不做无证据的猜测修复，改为让故障可见（IPC 自检灯 + 双侧错误显式化），待用户复测定位
2. **扫描引擎性能缺陷（真盘测试时意外发现）**
   - jwalk 的 `DirEntry::metadata()` 每次调用执行 `fs::symlink_metadata(path)`——每文件一次额外系统调用，且在单线程消费端串行执行；NVMe 上实测仅 ~3,000 文件/秒
   - `std::fs::read_dir` 的 `DirEntry::metadata()` 在 Windows 上直接使用目录枚举缓存，零额外系统调用——jwalk 未利用此优势
   - 解决：移除 jwalk 依赖，rayon `scope_fifo` 自研并行遍历（每目录一个任务、主线程增量聚合、逐条目取消检查）
   - 遇到的编译/逻辑问题：E0308（match 分支 `fetch_add` 返回 u64 未加分支块）、生命周期（`walk_dir` 需把 ctx 借用与 scope env 绑定为同一 `'env`）、聚合漏加目录自身直属统计（单测抓到，修复）
3. **质量门禁链的教训**：`cmd1; cmd2; if ($LASTEXITCODE)` 链中前面的命令失败仍会打印后面的 GREEN——改为每步显式检查退出码。教训：**验证脚本的退出码逻辑本身也要验证**
